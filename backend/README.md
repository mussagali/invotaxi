# InvoTaxi Backend — план проекта

Пакет документов для создания продакшен-бэкенда InvoTaxi на базе
существующего алгоритма распределения заказов (invotaxi_routing_toolkit).

## Состав

| Файл | Что внутри |
|---|---|
| [01-CODE-REVIEW.md](01-CODE-REVIEW.md) | Ревью текущего скрипта: баги B1–B8, что чинить при переносе |
| [02-ARCHITECTURE.md](02-ARCHITECTURE.md) | Полная архитектура: стек, схема данных, потоки, безопасность, нагрузка |
| [03-ORCHESTRATION.md](03-ORCHESTRATION.md) | Регламент: Fable — дирижёр, Codex 5.6 — кодер; цикл этапа, gates |
| [04-SERVER-REQUIREMENTS.md](04-SERVER-REQUIREMENTS.md) | Требования сервера на 1000–1500 онлайн: минимум 2vCPU/4ГБ, рекомендовано 4vCPU/8ГБ |
| [prompts/](prompts/) | 11 готовых промтов P0–P10, по одному на этап |

## Как запустить работу

1. Открой новую сессию в папке будущего репо `invotaxi-backend`.
2. Скажи Fable: «Работаем по invotaxi-backend-plan, начинай с P0,
   регламент — 03-ORCHESTRATION.md». К промту P5 приложи папку
   `invotaxi_routing/` из архива (исходники движка).
3. Fable отдаёт промты Codex по одному, после каждого этапа сам
   запускает тесты и проверяет Definition of Done, при замечаниях
   возвращает Codex на доработку (до 3 итераций).
4. После P9 в 04-SERVER-REQUIREMENTS.md появятся ЗАМЕРЕННЫЕ
   (а не оценочные) минимальные требования сервера.
5. После P10 бэкенд задеплоен; мобильное приложение подключается по
   OpenAPI-схеме (`/api/v1`, автогенерация SDK), realtime — WebSocket
   `/api/v1/ws`, переходный импорт заказов со старой платформы —
   `POST /api/v1/orders/import`.

## Ориентир по срокам (ИИ-кодер + дирижёр)
P0–P2: 1–2 дня · P3–P4: 1–2 дня · P5 (движок): 2–3 дня ·
P6–P7: 2–3 дня · P8: 1 день · P9: 1–2 дня · P10: 1 день.
Итого ~1.5–2 недели до боевого деплоя при плотной работе.
