# Ревью invotaxi_routing_toolkit — найденные проблемы

Проверены все 10 файлов (~1400 строк). Алгоритм в целом рабочий и логика
соответствует README, но есть реальные баги, которые надо закрыть при
переносе в бэкенд. Нумерация B1..B8 — на неё ссылаются промты (P5).

## Критичные

### B1 — вместимость (места) НЕ проверяется в основном пути вставки
`routing_core.try_append_trip()` / `build_sequential_route()` /
`find_driver_for_order()` нигде не сверяют `total_seats` заказа с
`route.capacity`. После схлопывания близнецов представитель группы несёт
`total_seats` до 4–6 мест (2-3 человека × сопровождение), но при обычной
жадной вставке он спокойно попадает в седан с capacity=4 и даже это не
проверяется. То же в `minivan_runs.try_build_run()` — считается только
число заказов (≤3), а не мест: 3 близнецовых представителя могут дать
8+ мест в 6-местном минивэне.
Проверка мест есть ТОЛЬКО в pooling.py (`seats_of`).
**Фикс:** проверять `sum(total_seats) <= capacity` в момент, когда заказы
физически пересекаются в машине (для Trip — просто заказ ≤ capacity, для
Run — сумма по группе), плюс добавить эту проверку в `validate_solution()`.

### B2 — `pool_leftover_groups`: кандидаты не отсортированы
`pooling.py:151` — `pool = pool[:5]`, но `pool` собирается итерацией по
`set` и НЕ отсортирован по расстоянию (в отличие от `minivan_runs`, где
есть `pool.sort()`). Берутся 5 произвольных кандидатов, а не 5 ближайших —
качество группировки случайное.
**Фикс:** собирать `(d, cand)`, сортировать, брать топ-5.

## Средние

### B3 — обед: разрыв до первой и после последней поездки игнорируется
`lunch.py` — комментарий обещает «разрыв перед первой поездкой», но цикл
стартует с `prev_end=None`, поэтому первый (и последний) разрыв дня
никогда не рассматриваются. Водитель с первой поездкой в 13:00 не получит
обед 10:30–12:30, хотя окно свободно.

### B4 — `RENTAL_MIN_ORDERS = 11` объявлен и нигде не используется
README называет его «целевой минимум на арендованную машину», по факту
аренда не консолидируется и минимум не проверяется.

### B5 — `consolidate()` всегда возвращает пустой set
Возвращаемое значение мёртвое — вводит в заблуждение вызывающего.

## Важно при переносе в онлайн-бэкенд (в батче — не баги)

### B6 — вставка/пересборка не учитывает уже назначенный обед
Сейчас обед назначается ПОСЛЕ маршрутизации, поэтому конфликтов нет. В
онлайн-режиме (дозаказ в течение дня) пересборка маршрута может съесть
обед. В бэке `build_sequential_route` должен уважать `route.lunch`.

### B7 — водитель «ещё не в работе» телепортируется к первому заказу
`try_append_trip` при `free_time is None` ставит
`earliest_arrival = target - 15` независимо от расстояния от стартовой
позиции. Для планирования «на завтра» это ок (водитель выедет заранее),
для распределения в реальном времени — неверно.

### B8 — pandas/deepcopy в горячем пути
`consolidate()` делает `deepcopy` всех маршрутов до 60 раз, доступ к
данным — через `orders_df.loc[]` на каждый чих. Для батча на сотни заказов
приемлемо; в бэкенде движок надо запускать только в фоновом воркере
(не в HTTP-запросе) и по-хорошему заменить pandas в горячем пути на
dict/dataclass (ускорение на порядок, см. промт P5).

## Мелочи
- `region_builder.consolidate`: `tried_victims.discard(victim)` после
  успеха позволяет распускать одного водителя многократно — защищено
  только safety-счётчиком 60.
- Близнецы матчатся по ДОСЛОВНОМУ совпадению адреса
  (`groupby(['тел_норм','Откуда','Куда','Время'])`) — «Авангард 3» vs
  «Авангард, 3» уже не близнецы. При переносе на платформу близнецов
  лучше определять по ID клиента/заявки, а не по строкам.
- `geo_utils.bank_of` вызывается по 2 раза на каждую пару точек в самом
  горячем цикле — в бэке кешировать (lru_cache по округлённым
  координатам).

## Вывод
Алгоритм переносить можно: стадийность (минивэны → седаны → консолидация
→ пулинг → аренда), транзакционная консолидация и честный список
исключений — правильные решения. Обязательные фиксы перед продом:
B1, B2 (+ проверка мест в валидаторе), B6 для онлайн-режима.
