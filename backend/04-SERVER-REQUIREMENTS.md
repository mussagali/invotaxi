# Требования к серверу (1000–1500 онлайн)

Профиль нагрузки — не «1500 RPS», а 1350–1500 одновременных пользователей:
около 70–150 RPS, долгоживущие WebSocket, GPS-пинги в Redis и периодический
CPU-тяжёлый расчёт маршрутов в отдельном ARQ worker.

## Минимальная измеренная конфигурация

Всё на одном VPS под Docker Compose:

| Ресурс | Минимум | Комментарий |
|---|---|---|
| CPU | **4 vCPU** (совр. x86, ≥2,5 ГГц) | 2 API worker + ARQ worker; подтверждено 30-минутным P9 |
| RAM | **8 ГБ** | контейнеры в измеренном пике <700 МиБ суммарно; остальное — ОС, page cache, мониторинг и запас |
| Диск | **40 ГБ NVMe/SSD** | треки растут ~50–150 МБ/день до ретенции; HDD нельзя |
| Сеть | **100 Мбит/с** | достаточно для измеренного API/GPS/WS трафика |
| ОС | **Ubuntu 24.04 LTS** | целевая production ОС |

На минимуме обязательны: swap 2 ГБ как страховка (не рабочая память), resource
limits контейнеров, ретенция `driver_track_history` ≤30 дней и внешний backup.

## Рекомендуемая конфигурация

| Ресурс | Рекомендуется |
|---|---|
| CPU | **8 vCPU** |
| RAM | **16 ГБ** |
| Диск | **80–100 ГБ NVMe** |
| Доп. | ежедневные backup PostgreSQL на второй носитель/object storage |

8 vCPU / 16 ГБ — запас ×2 относительно минимального прошедшего профиля: для
обновлений, backup/restore, роста данных и одновременных тяжёлых операций.

## Замерено

Оба профиля прогнаны по 30 минут: ramp-up 3 минуты, затем 27 минут steady;
250 водителей + 1100 клиентов (1350 WS), GPS каждые 7 секунд, 150 запросов
диспетчера/мин и dispatch-job на 600 заказов с 10-й минуты.

| Профиль | Итог | HTTP p95 | HTTP errors | WS disconnect | RPS | Dispatch 600 |
|---|---|---:|---:|---:|---:|---:|
| 2 vCPU / 4 ГБ | **FAIL** | 9 995,0 мс | 0,0458% | 56,5487% | 69,98 | 9,46 с |
| 4 vCPU / 8 ГБ | **PASS** | 17,7 мс | 0,0000% | 0,0000% | 72,87 | 5,11 с |

На 4/8 API p95 driver/client/dispatcher = 14,0/19,0/32,1 мс; peak RAM
API/worker/PostgreSQL/Redis = 447,7/141,5/118,7/8,4 МиБ; steady CPU =
56,8/9,9/4,0/4,5%. Dispatch не поднял p95 выше 300 мс.

На 2/4 dispatch завершился, но API накопил очередь, один раз временно перешёл в
degraded health во время ramp-up, а latency и WS thresholds были провалены.
Поэтому 2/4 не является допустимым production-минимумом.

Источник цифр: `loadtest/results/*.md` и `loadtest/CONCLUSION.md`. Матрицу нужно
повторять после значимых изменений кода, базы, Docker/ядра или железа.

## Путь масштабирования (1500 → 5000+)

1. Вынести PostgreSQL на отдельный узел или managed service.
2. Добавить API-реплики за reverse proxy; realtime уже использует Redis pub/sub.
3. При необходимости выделить GPS ingest в отдельный лёгкий сервис.
