# P9 — Нагрузочное тестирование, мониторинг, замер сервера

## Роль
Senior SRE/perf-инженер. Проект invotaxi-backend (P0–P8 готовы). Задача:
доказать, что система держит 1000–1500 онлайн-пользователей, поставить
мониторинг и определить фактические минимальные требования сервера.

## Скоуп
1. Мониторинг:
   - `/metrics` (prometheus-fastapi-instrumentator): латентности по
     эндпойнтам, RPS, in-flight, ошибки; кастомные метрики: активные
     WS-соединения, размер очереди ARQ, длительность dispatch-job,
     GPS-пинги/с, отброшенные аномалии;
   - docker-compose.monitoring.yml: Prometheus + Grafana + дашборд
     (JSON в репо): API p50/p95/p99, RPS, WS, CPU/RAM контейнеров
     (cadvisor), PG connections, Redis ops;
   - alert-правила (файл): p95 > 500 мс 5 мин, ошибки > 1%, диск > 80%,
     dispatch-job > 15 мин.
2. k6-сценарий `loadtest/day_peak.js` (параметры через ENV):
   - 250 VU «водители»: логин, WS-подключение, POST location каждые 7 с;
   - 1100 VU «клиенты»: WS + GET статуса заказа раз в 30–60 с,
     5% создают заказ;
   - 150 VU-запросов/мин «диспетчер»: списки, планы, live-карта;
   - через 10 минут теста параллельно стартует dispatch-job на
     600 заказов (сид-генератор из P5);
   - длительность 30 мин, ramp-up 3 мин.
   - Пороги (thresholds в k6): http p95 < 300 мс, ошибки < 0.1%,
     ws-disconnect < 1%.
3. Скрипт `loadtest/run_matrix.sh`: прогоняет сценарий на прод-профиле
   compose с ограничениями ресурсов последовательно:
   `2cpu/4g`, `4cpu/8g` (docker compose deploy limits). Итог каждого
   прогона — `loadtest/results/{profile}.md`: пороги пройдены/нет,
   p95 по группам, пик RAM по контейнерам, CPU steady, длительность
   dispatch-job.
4. Тюнинг по результатам (делать только при провале порогов, каждое
   изменение — отдельным коммитом с цифрами до/после): число воркеров
   uvicorn, пул PG (+ PgBouncer при нехватке коннектов), индексы по
   pg_stat_statements, batch-размеры ингеста.
5. Итог: `loadtest/CONCLUSION.md` — таблица профилей, вывод «минимальная
   конфигурация — X vCPU / Y ГБ», рекомендация X×2. Этот файл — источник
   для 04-SERVER-REQUIREMENTS.md (раздел «Замерено»).

## Definition of Done
- [ ] метрики отдаются, дашборд Grafana импортируется и живой
- [ ] k6-сценарий запускается одной командой против compose
- [ ] есть results/*.md минимум для двух профилей ресурсов
- [ ] на профиле 4cpu/8g все пороги пройдены (если нет — тюнинг и
      повтор, история в коммитах)
- [ ] dispatch-job на 600 заказов под нагрузкой завершается и не
      роняет p95 API выше порога
- [ ] CONCLUSION.md с обоснованными минимальными требованиями
- [ ] никаких изменений бизнес-логики в этом этапе (только perf/infra)
