# Регламент оркестрации: Fable — дирижёр, Codex 5.6 — кодер

Как вести проект: Fable (эта сессия Claude Code) управляет процессом,
Codex 5.6 (sol, medium) пишет основной код по промтам из `prompts/`.

## Роли

**Fable (дирижёр):**
- выдаёт Codex промты строго по одному этапу (P0 → P10, по порядку);
- после каждого этапа ЗАПУСКАЕТ проект и тесты сам (не верит на слово);
- делает код-ревью диффа этапа (сениор-планка: корректность, границы
  транзакций, N+1, обработка ошибок, безопасность);
- решает: принять этап / вернуть Codex на доработку с конкретным
  списком замечаний / починить мелочь самому;
- ведёт файл `PROGRESS.md` в репо: этап, статус, что осталось;
- по итогам P9 фиксирует замеренные минимальные требования сервера.

**Codex (кодер):** получает один промт целиком, пишет код + тесты,
не выходит за скоуп этапа, не трогает чужие этапы без указания.

## Цикл одного этапа

```
1. Fable отдаёт Codex промт Pn (файл целиком, без сокращений)
2. Codex пишет код и тесты
3. Fable: docker compose up -d && pytest -x -q
   - красные тесты / не поднялось → пункт 5
4. Fable: ручная проверка Definition of Done из промта
   (каждый пункт чек-листа руками/скриптом, не «на глаз»)
5. Есть замечания → Fable формирует список «FIX:» (конкретно: файл,
   строка, что не так, как надо) → Codex правит → снова п.3
   Максимум 3 итерации; если не сходится — Fable чинит сам и
   записывает причину в PROGRESS.md
6. Этап принят → git commit (один этап = минимум один коммит,
   сообщение: "P3: orders API + lifecycle") → следующий промт
```

## Жёсткие правила (gates)

1. **Нельзя начинать Pn+1, пока не приняты все DoD-пункты Pn.**
2. **Тесты этапа не удаляются и не ослабляются** следующими этапами.
   Регрессия = блокер.
3. Покрытие: `routing/` ≥ 90% (это ядро бизнеса), `app/services` ≥ 80%,
   роутеры — интеграционными тестами.
4. Каждый баг из 01-CODE-REVIEW.md (B1–B7) закрывается ОТДЕЛЬНЫМ
   тестом, который падает на старом поведении (проверить: тест написан
   до фикса и красный).
5. Любой эндпойнт: авторизация + проверка роли + валидация входа.
   Fable на ревью пробует минимум один негативный сценарий руками
   (чужой заказ, просроченный токен, кривой payload).
6. Секреты только в `.env` (не в коде, не в compose), `.env.example`
   поддерживается актуальным.
7. `ruff + mypy` зелёные в CI — иначе этап не принят.

## Правила общения с Codex

- Один промт = одно сообщение, без «продолжи потом».
- В промте всегда есть: контекст, скоуп, файлы, DoD, тесты. Если Codex
  задаёт вопрос, ответ даёт Fable (сам решает в духе 02-ARCHITECTURE.md),
  а не пользователь.
- Если Codex предлагает отклониться от архитектуры — по умолчанию
  отказ; исключение допускается, только если Fable убедился, что это
  упрощение без потери требований, и записал решение в PROGRESS.md.

## Как Fable определяет минимальные требования сервера (P9)

Не «прикидкой», а замером:
1. Поднять прод-профиль compose на машине с ограничениями
   (`cpus: 2, mem_limit: 4g` — затем 4/8).
2. k6-сценарий «боевой день»: 1500 VU (250 водителей шлют GPS каждые
   7 с, 1100 клиентов держат WS + редкий polling, 150 диспетчерских
   запросов/мин), параллельно запустить dispatch-job на 600 заказов.
3. Пройдено = p95 API < 300 мс, ошибок < 0.1%, WS-разрывов < 1%,
   dispatch-job завершился, OOM нет, CPU steady < 70%.
4. Минимальная конфигурация = наименьшая, прошедшая критерии;
   рекомендуемая = минимальная × 2 по памяти + 1 ступень CPU.
5. Результат записать в 04-SERVER-REQUIREMENTS.md (раздел «Замерено»).

## Порядок этапов

| # | Промт | Что даёт | Зависит от |
|---|---|---|---|
| P0 | Каркас: repo, docker, CI, healthcheck | скелет | — |
| P1 | Схема БД + миграции + сиды | данные | P0 |
| P2 | Auth + RBAC | доступ | P1 |
| P3 | Orders API + state machine | заказы | P2 |
| P4 | Drivers + GPS-ингест (Redis GEO) | телеметрия | P2 |
| P5 | Порт routing/ + фиксы B1–B7 + golden-тесты | ядро | P0 (изолирован!) |
| P6 | Dispatch: job, draft-план, правки, publish | распределение | P3,P4,P5 |
| P7 | Realtime: WS + pub/sub + уведомления | live | P4,P6 |
| P8 | Отчёты: Excel-шаблоны, статистика | диспетчер | P6 |
| P9 | Нагрузка: k6 + Prometheus + тюнинг + замер сервера | проверка | P7 |
| P10 | Prod-деплой: TLS, бэкапы, runbook | запуск | P9 |

P5 не зависит от БД — его можно отдать Codex параллельно с P2–P4,
если ведётся в отдельной ветке.
